# Repository instructions

## Purpose

This repository contains the Relationship Operating Framework: an independent
documentation framework for long-term relationship stewardship.

## Authority

Apply this order:

1. Direct current owner instruction.
2. `framework/charter.md`.
3. `GOVERNANCE.md`.
4. Canonical documents under `framework/`.
5. Repository contribution, conduct, security, and release guidance.
6. Examples.
7. Research and project review records.

Lower-authority material cannot silently redefine higher-authority material.

The framework adopts Open Framework Commons `v1.0.0` at commit
`a0f0d384e9010a65d1a21a324b4c912433d5e031` by reference. If Commons and local
guidance appear to conflict, stop and surface the conflict. Do not silently copy,
reinterpret, or change Commons.

## Framework boundaries

- Put people first and treat relationships as human realities, not records,
  assets, stages, or scores.
- Keep relationship ownership and external action under accountable human
  judgment.
- Permit agents to assist with bounded preparation, continuity, and reflection;
  never grant them autonomous authority to contact, score, manipulate, or
  transact with people.
- Keep the method independent of software, vendors, models, databases, schemas,
  protocols, automations, and machine-specific representations.
- Do not turn this into a sales framework, CRM specification, outreach engine,
  application, runtime, CI system, or conformance layer.
- Keep Relationship distinct from Influence. Relationship owns durable
  stewardship across time, not Influence's contribution and community-growth
  method.
- Keep first-user, first-job, lifecycle, domain-model, Mission Control, and
  extension ideas labeled as proposals until accepted through governance.
- Examples illustrate the framework and never create requirements or evidence
  of effectiveness.

## Documentation

- Write direct, clear Markdown for people and assisting agents.
- Use relative links for repository content and exact links for adopted external
  releases.
- Use lowercase kebab-case within content directories, except for conventional
  directory indexes named `README.md`; use uppercase conventional names for
  repository-wide policy files.
- Separate principle, experience, proposal, validated finding, example, and open
  question.
- Use fictional public examples unless real material is explicitly authorized,
  safely sourced, and necessary.
- Keep private relationship context, personal data, prompts, local paths, tool or
  model names, and private planning history out of public records.
- Add no scripts, automation, CI, schemas, or generated artifacts to the initial
  documentation release.

## Verification

Before reporting completion:

- inspect status, diff, branch, remote, and authorship;
- check every local Markdown link and heading target;
- compare canonical vocabulary and authority statements across the repository;
- confirm proposals remain visibly non-normative;
- inspect every public file for private history, identities, unsupported claims,
  and fabricated evidence;
- run independent practical, adversarial, coherence, and public-hygiene reviews
  against an exact candidate commit;
- resolve material findings and rerun affected reviews; and
- compare the merged tree with the reviewed candidate before release.
